# MOSS-Image 提示词编写原则

MOSS-Image 的正向提示词只有两种合法形态：**Caption**（一段连贯的散文）或 **Layout**（编译后的一行 JSON）。二选一，不要混写，也不要套模板段落标签。

## 先决定用哪一种

MOSS 接受**三种输入形态，可以混写**：

| 形态 | 什么时候用 | 说明 |
|---|---|---|
| **JSON Layout** | **多人、多元素、要控层级、带文字、要版式** | 质量最高的一档。位置由坐标钉死，模型不会自己乱排。 |
| **自然语言 Caption** | 单人、简单场景、氛围图、概念图 | 位置一句话能说清时它更自然，别硬上 JSON。 |
| **Tag 串** | 动漫向、角色明确的同人图 | 靠 danbooru 式标签点名角色与动作。 |

**判据一句话：画面里「谁在哪」需要靠猜的时候，就上 JSON。**

- 三四个元素以内、位置能用「在她左边」「窗在她身后」说清 → Caption 够用。
- **凡是要定位的场合一律写 JSON**，不只人多：构图、多人物、多元素、海报/版面设计、要卡住某块空间、要出可读文字——全部走 JSON。用长散文硬描述坐标是白费劲：模型不认文字里的方位词，只吃大致倾向，越写越长反而互相稀释。
- **「写 JSON 慢」对 agent 不成立**：手写 JSON 确实比说话慢，但这恰恰是 agent 的优势区——一次算好坐标、一次写全，比反复用散文试错重跑省得多。**不要因为"怕麻烦"退回散文。**
- 两者可以混：JSON 管位置，`summary.caption` 里再写介质、光线、画风、配色这些**全局**属性。

**画面复杂不等于必须用 JSON，但「位置必须被框死」就一定是 JSON。**

## Caption 怎么写

一段连贯的散文，把可见的选择说清楚：

1. **主体与动作**——谁 / 什么，在做什么；
2. **相关外观**——看得见的那部分形貌（发色、材质、服装款式）；
3. **环境**——地点、陈设、季节、时间；
4. **镜头与取景**——景别、视角方向、主体在画幅里的位置与占比；
5. **介质**——照片 / 插画 / 油画 / 版画，用一句话定死，否则画风会飘；
6. **光线**——光源方向、硬软、时间感；
7. **材质**——金属、玻璃、织物、皮肤各自的反光与质感；
8. **色彩与情绪**——主色调，以及画面要传达的感觉。

规则：

- **空间关系用文字写**（"在她左侧的地板上""窗在她身后"），不要写坐标。
- **画面里要出现的文字，逐字写出来并用引号包住**，保持原文语言、标点、大小写与换行——不要翻译、不要改写、不要写"某某标题"这类占位。
- **要换行就在提示词里手写 `\n`**（或直接真的换行）。模型自己会折行，但折在哪不保证；追求正确率和精确断行时，断点必须由你指定。中文长句尤其如此。
- 指令里被引用的句子**不一定是画面文字**：分清"要画出来的字"和"你在引述的要求"。
- **自然语言里不要堆质量标签**（`masterpiece, best quality, 8k, ultra detailed` 这类）。散文里它们占注意力却不描述画面。**走 Tag 串时相反**，质量词是有效信号——见下一节。
- **不要写过程说明、不要定词数**。写多写少由画面本身决定：brief 本来就极简时保持极简，brief 丰富时把它展开，而不是套成"标题 + 主体 + 页脚"的通用版式。
- **用户给的东西一样不许改**：主体、数量、关系、介质、风格、排除项、指定文字——照写。数量是"三"就写 three，不要写成"若干"。
- **设计类画面（海报 / 卡片 / 信息图）图文一起构思**：先定阅读顺序与主次，再排文字块；文案要写真实内容，不许写"此处填标题"。
- 不要从参考图里搬来无关的人名、水印、标语。

## Tag 串怎么写

动漫向题材、角色明确的图，用 danbooru 式标签串比散文更准——角色名、作品名、动作都是现成的强锚点。

**官方规定的构造顺序**（照这个顺序排，效果最好）：

> Quality → Score → Meta → Year → Character → Series → Artist → General

例：`best quality, highres, hatsune miku, vocaloid, @foo bar, 1girl, blue hair`

- 质量词（`best quality` / `highres` / `masterpiece`）**放最前面**，别散在句中；
- 角色名 → 作品名 → 画师（有就写 `@画师名`）→ 通用描述（人数、发色、服装、动作、构图）；
- 角色串负责长相，**不要在角色名后再补发色瞳色**——补了会覆盖角色设定；
- 数量要写死（`1girl`、`2girls`、`6+girls`），不写模型自己猜；
- Tag 串与自然语言可以混写：标签打底，末尾接一两句自然语言交代光线、氛围、版面。

## Layout 怎么写

Layout 是一份 JSON 草稿，经官方工具编译成一行可投喂的提示词。**宽高必须是 16 的倍数**，且与出图时选的分辨率一致。

### 两套 schema，按用途选

| 用途 | 结构 | 适合 |
|---|---|---|
| **讲戏型** | `scene_type` + `gen_brief` + `elements[]` | 群像、有动作串联与情节的场面。`gen_brief` 用一整段散文讲清谁在哪个方位、谁压谁、动势从哪到哪 |
| **排版型** | `summary.caption` + `items[]` | 海报、版面、带可读文字、需要干净几何分割的图 |

两套的坐标约定相同。**拿不准就用排版型**——它的字段有官方文档背书，`text` 项的位置也最好控。

### 四步把布局搭出来

**① 先定层级，再分框。** 不要一上来就给人分配坐标。先决定这幅画有几层（背景 / 中景 / 前景），每层放几个单元，然后按层分配 y 轴范围：背景占满画布，中景在上半，前景在下半。**y 范围先划死，x 再按左右位置分**，这样永远不会排成一条横线。

**② 一个人物一个框，框只圈住这个人。** 相邻的人可以框框交叠（这是允许的，也是该有的），但**一个人的框里不要塞进去两个人**。

**③ 每个人的 caption 写四件事**，缺一件模型就自己编：

1. **名字 + 作品**（模型认得的角色名就写，不认识就改写成可辨识的外貌）
2. **与邻居的方位关系**（`behind X and above-right of Y`——这句是把人物钉在框里的关键，比坐标还重要）
3. **服装与外观**（款式、颜色、标志性配件）
4. **动作与表情**（在做什么、看哪里、什么神态）

**④ 校一遍重叠关系。** 允许压肩、压下半身、压裙摆；**脸绝对不许被压**。这条要写进 `gen_brief` 或 summary，而且要逐个交代谁遮谁。

### 文字项单独成 item

- `label: "text"`，`text` 放**逐字原文**（大小写、标点、换行都照原样）
- `caption` 写字体观感与处理方式（粗无衬线、斜排、加底衬条、反白）
- **框就是它占的版面**：字号靠框的高度控，不靠「很大的字」这种形容词
- 一幅里 2–4 处文字最稳；超过就等着崩字，先把装饰性小字砍掉

### 三条硬规则

1. **框是定位标注，不是让人画出边框、分格或贴纸。** 不要写「加一个框」。
2. **框越界会被拒绝，不会自动裁掉。** 算坐标时按半宽半高（±W/2、±H/2）核一遍。
3. **同一份 JSON 只用一个坐标约定**，改了几何就整份重算，别混着来。

### 改稿时

先重读原文，**只改受影响的那几条 caption / bbox**，别顺手重写没被点名的部分。加人不是加一条元素就完事——要给新角色在总述里分好位置，并把被挤动的邻居方位一起改写。

## 坐标有两套格式，别混

- **草稿格式**（GitHub 那个编译器吃的）：`abs` + `xyxy`，`[x_min, y_min, x_max, y_max]`，原点在**画布左上角**，普通像素坐标。
- **模型输入格式**（直接投喂给 MOSS 的）：`abs_centralized` + `yxyx`，`[y_min, x_min, y_max, x_max]`，原点在**画布中心**，x 向右、y 向下。宽 W、高 H 的画布范围是 −W/2…+W/2、−H/2…+H/2。

## 怎么产出可投喂的 Layout

**本机走 ComfyUI 原生节点，不用写脚本**：

1. `Create Bounding Boxes` 里在画面上拖框，每个框填 `desc`（要画什么），文字框再填 `text`（逐字原文）；
2. 接 `MOSS-Image Layout Prompt`，把整图描述填进它的 `prompt`，`width` / `height` 填成图尺寸（16 的倍数），要当角色标注的框号写进 `character_boxes`（如 `"1, 3"`）；
3. 它的输出就是一行可直接用的 Layout JSON（`abs_centralized` / `yxyx` 已转好），接进正向提示词。

**没有界面时**才用官方 `compile_prompt.py`：喂草稿（`abs`/`xyxy` + 宽高 + `summary` + `items`），它输出**同一条**已换算的 JSON 行。编译报错就改草稿再编译，不要手写一份"居中版"绕过校验。

无论走哪条路，宽×高都写在提示词之外，出图时按同一组数字设分辨率；框越界会被拒绝而不是自动裁掉。

## 放进本地工作流时

- 正向提示词里**只放 Caption 全文，或编译后的那一行 Layout JSON**。JSON 字段解释、坐标换算过程、工具指令都不是画面内容，写进去会被当成要画的东西。
- Layout 用的尺寸必须和 `--ratio` / `--megapixels` 算出来的实际宽高一致，否则框会整体偏移。
- 需要渲染的文字越多越容易崩：先砍掉装饰性小字，保住大标题与必需信息。

## JSON 不管的三件事

别把 JSON 当万能药，它只解决「谁在哪」，这三件它一概管不了：

1. **画风与质感压不住。** 想要三色限制、版画 / 剪贴 / 丝网印、duotone 这种「把画面压成两三种墨」的效果，JSON 一点忙都帮不上——那得靠 caption 里的介质句和配色句去压，而且**开了风格 LoRA 时基本压不过**（LoRA 的方向和受限调色板常常是反的）。
2. **人数上限不由提示词决定。** 十个以上时，位置能排开，但**手指、道具的持有关系、小配饰会在快档下糊掉**。这不是 JSON 写得好不好的问题，是采样档位的问题（步数、CFG、是否挂着蒸馏加速）。
3. **不会替你决定视觉重心。** 框分配得再工整，画面也可能平——重心要靠「一个大主体 + 其余递减」的尺寸差做出来，框的大小就是你的音量旋钮，得自己调。
